# v0.3.2 — 调色板点的颜色终于真的生效了

一句话：**颜色值一直是 8 位，解析器只认 6 位**，所以每点一次色板，颜色都被静默丢弃、回落到白色。不是渲染慢，也不是没保存。

## 根因

色板写进配置的是 `#AARRGGBB`（八位，带 alpha）：

```
BarsColor=#FFE5484D
```

而 `CardWindow` 自己那份 `ParseHex` 只接受六位：

```csharp
if (h.Length != 6) return false;      // 八位一律拒
```

于是 `ResolveBarsColour()` 每次都解析失败，回落到白色。`config.ini` 里存的是对的、日志也在打，但打的是原始字符串而不是解析结果——看起来成功，实际什么都没变。重启也一样：读到的还是同一个八位字符串。

顺带说明为什么以前"偶尔像是好的"：手输过六位色值（`#E5484D`）的时候是正常的；从色板点的一律不行。

## 改了什么

- `CardWindow.ParseHex` 现在接受 `#RGB`/`#RRGGBB`/`#AARRGGBB` 三种写法，八位按 alpha + RGB 解析；
- 日志加上解析结果，这类问题以后藏不住：
  `bars recolour #FFE5484D|| -> #FFE5484D`
- 颜色比对挪到**每帧路径**（`StepBars` 开头一次字符串比较），不再依赖某条调用链是否走到；
- `ApplyLook()` 在 `if (_title == null) return;` **之前**先重绘一次，卡片空闲/隐藏时改色也不会被吞。

## 影响面

同一个解析器还负责**进度条轨道色、进度条填充色、下方按钮色**等模块级颜色。也就是说这一修同时修好了：

- 频谱颜色
- 进度条轨道 / 填充颜色
- 下方按钮颜色

（文字颜色走的是另一条路，本来就是对的。）

## 验证

截卡取样（PrintWindow 后逐像素统计）：选 `#E5484D` 后条子主色为 `(217, 68, 73)`，即 `#E5484D` × 94% 不透明度的实际值；修复前是 `(175, 175, 175)` 的灰白。
